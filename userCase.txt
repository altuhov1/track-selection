ДОКУМЕНТАЦИЯ ПОЛЬЗОВАТЕЛЬСКИХ СЦЕНАРИЕВ (USE CASES)
======================================================

РОЛИ ПОЛЬЗОВАТЕЛЕЙ
------------------
1. Студент (student) - выбирает треки, получает рекомендации, управляет профилем
2. Администратор (admin) - управляет каталогом треков (CRUD операции)
3. Неавторизованный пользователь - только регистрация, вход и просмотр треков


================================================================================
USE CASES ДЛЯ НЕАВТОРИЗОВАННОГО ПОЛЬЗОВАТЕЛЯ
================================================================================

UC-01: РЕГИСТРАЦИЯ В СИСТЕМЕ
------------------------------
Актор:               Неавторизованный пользователь
Предусловие:         Пользователь не зарегистрирован
Постусловие:         Создана учетная запись
Основной сценарий:   
 1. Пользователь отправляет POST /register
 2. Передает email, password (мин. 6 символов), role (student/admin), 
    first_name, last_name
 3. При role=admin обязательно передает admin_secret
 4. Система создает пользователя, возвращает статус 201
Альтернативы:        
 - Email уже существует → ошибка 409
 - Неверный admin_secret → ошибка 400 (ADMIN_SECRET_REQUIRED/INVALID_ADMIN_SECRET)
 - Пароль короче 6 символов → ошибка 400

UC-02: ВХОД В СИСТЕМУ
-----------------------
Актор:               Зарегистрированный пользователь
Предусловие:         Пользователь имеет учетную запись
Постусловие:         Получен JWT токен
Основной сценарий:   
 1. Пользователь отправляет POST /login
 2. Передает email и password
 3. Система проверяет учетные данные
 4. Возвращает JWT токен
Альтернативы:        
 - Неверные email или пароль → ошибка 401

UC-03: ПРОСМОТР ВСЕХ ТРЕКОВ (ПУБЛИЧНЫЙ)
-----------------------------------------
Актор:               Любой пользователь (включая неавторизованных)
Предусловие:         В системе есть хотя бы один трек
Постусловие:         Пользователь видит список треков
Основной сценарий:   
 1. Пользователь отправляет GET /all-tracks
 2. Система возвращает массив всех треков


================================================================================
USE CASES ДЛЯ СТУДЕНТА (STUDENT)
================================================================================

UC-06: ПРОСМОТР СВОИХ ПРЕДПОЧТЕНИЙ
------------------------------------
Актор:               Студент
Предусловие:         Авторизован
Постусловие:         Получены предпочтения
Основной сценарий:   
 1. Студент отправляет GET /me/info
 2. Система возвращает объект Preferences с полями:
    - professional_goals (массив int)
    - grades (оценки по предметам от 2 до 5)
    - skills (навыки от 0 до 10)
    - learning_style (1,2,3)
    - certificates (0 или 1)
Альтернативы:        
 - Нет токена → ошибка 401

UC-07: ЗАПОЛНЕНИЕ / ОБНОВЛЕНИЕ ПРЕДПОЧТЕНИЙ
---------------------------------------------
Актор:               Студент
Предусловие:         Авторизован
Постусловие:         Предпочтения сохранены
Основной сценарий:   
 1. Студент отправляет POST /me/edit-info
 2. Передает любые из полей:
    - professional_goals (массив int)
    - grades (объект с оценками 2-5)
    - skills (объект с навыками 0-10)
    - learning_style (1/2/3)
    - certificates (0/1)
 3. Система сохраняет данные, возвращает статус 200
Альтернативы:        
 - Некорректные значения → ошибка 400
 - Нет токена → ошибка 401

UC-08: ПОЛУЧЕНИЕ РЕКОМЕНДАЦИЙ ТРЕКОВ (PROMETHEE), ТОЛЬКО ЕСЛИ ЗАПОЛНЕН ПРОФИЛЬ ПОЛНОСТЬЮ
--------------------------------------------------
Актор:               Студент
Предусловие:         Профиль полностью заполнен:
                     - professional_goals не пустой
                     - Все оценки (Grades) от 2 до 5
                     - Хотя бы один навык (Skills) > 0
                     - learning_style = 1,2 или 3
Постусловие:         Получен отсортированный список рекомендаций
Основной сценарий:   
 1. Студент отправляет GET /student/recommendations
 2. Система применяет метод PROMETHEE для расчета
 3. Возвращает массив TrackScore с полями:
    - track_id, track_name
    - score (0-1), rank
    - criteria_scores (оценки по критериям)
Альтернативы:        
 - Профиль не заполнен полностью → ошибка 400 (PROFILE_NOT_COMPLETE)
 - Нет токена → ошибка 401

UC-09: ВЫБОР ТРЕКА
--------------------
Актор:               Студент
Предусловие:         Авторизован, трек существует
Постусловие:         Трек добавлен в список выбранных
Основной сценарий:   
 1. Студент отправляет POST /student/select-track
 2. Передает track_id (uuid)
 3. Система добавляет трек, возвращает статус 200
Альтернативы:        
 - Трек не найден → ошибка 404
 - Нет токена → ошибка 401

UC-10: ПОЛУЧЕНИЕ ВЫБРАННЫХ ТРЕКОВ
-----------------------------------
Актор:               Студент
Предусловие:         Авторизован
Постусловие:         Получен список выбранных треков
Основной сценарий:   
 1. Студент отправляет GET /student/selected-tracks
 2. Система возвращает объект с массивом tracks
Альтернативы:        
 - Нет токена → ошибка 401

UC-11: ОТМЕНА ВЫБОРА ТРЕКА
----------------------------
Актор:               Студент
Предусловие:         Авторизован, трек ранее был выбран
Постусловие:         Трек удален из списка выбранных
Основной сценарий:   
 1. Студент отправляет DELETE /student/unselect-track/{id}
 2. Передает id трека в path
 3. Система удаляет выбор, возвращает статус 200
Альтернативы:        
 - Выбор не найден → ошибка 404
 - Нет токена → ошибка 401


================================================================================
USE CASES ДЛЯ АДМИНИСТРАТОРА (ADMIN)
================================================================================

UC-12: СОЗДАНИЕ НОВОГО ТРЕКА
------------------------------
Актор:               Администратор
Предусловие:         Авторизован с ролью admin
Постусловие:         Новый трек добавлен в систему
Основной сценарий:   
 1. Админ отправляет POST /new-track
 2. Передает обязательные поля:
    - name, description
    - curriculum (структура с годами, семестрами, курсами)
    - requirements (массив с предметами и min_grade)
    - teachers (массив строк)
    - difficulty (1-5)
    - type (int)
    - employment_prospects (1-10)
    - alumni_reviews (1-10)
    - learning_style (1,2,3)
    - desired_tech_skills, desired_math_skills, desired_soft_skills (1-10)
 3. Опционально: web_link, has_certificates (0/1), professional_goals
 4. Система создает трек, возвращает объект Track с id
Альтернативы:        
 - Нет токена → ошибка 401
 - Роль не admin → ошибка 403
 - Некорректные данные → ошибка 400

UC-13: РЕДАКТИРОВАНИЕ ТРЕКА
-----------------------------
Актор:               Администратор
Предусловие:         Авторизован с ролью admin, трек существует
Постусловие:         Трек обновлен
Основной сценарий:   
 1. Админ отправляет PUT /edit-track/{id}
 2. Передает id в path
 3. Передает любые из полей трека для обновления
 4. Система обновляет трек, возвращает статус 200
Альтернативы:        
 - Трек не найден → ошибка 404
 - Нет токена → ошибка 401
 - Роль не admin → ошибка 403
 - Некорректные данные → ошибка 400

UC-14: УДАЛЕНИЕ ТРЕКА
-----------------------
Актор:               Администратор
Предусловие:         Авторизован с ролью admin, трек существует
Постусловие:         Трек удален из системы
Основной сценарий:   
 1. Админ отправляет DELETE /delete-track/{id}
 2. Передает id в path
 3. Система удаляет трек, возвращает статус 200
Альтернативы:        
 - Трек не найден → ошибка 404
 - Нет токена → ошибка 401
 - Роль не admin → ошибка 403


================================================================================
ОБЩИЕ ТРЕБОВАНИЯ И ОГРАНИЧЕНИЯ
================================================================================

1. АУТЕНТИФИКАЦИЯ
   - Все эндпоинты, кроме /register, /login и /all-tracks, требуют Bearer токен
   - Токен передается в заголовке: Authorization: Bearer <JWT-токен>

2. ВАЛИДАЦИЯ ПРЕДПОЧТЕНИЙ СТУДЕНТА
   - Оценки (Grades): от 2 до 5 по каждому предмету
   - Навыки (Skills): от 0 до 10
   - learning_style: 1 (визуал), 2 (аудиал), 3 (кинестетик)
   - certificates: 0 (нет), 1 (есть)

3. ВАЛИДАЦИЯ ТРЕКОВ
   - difficulty: от 1 (легкий) до 5 (сложный)
   - employment_prospects: от 1 до 10
   - alumni_reviews: от 1 до 10
   - desired_*_skills: от 1 до 10

4. СТРУКТУРА УЧЕБНОГО ПЛАНА (CURRICULUM)
   - Может быть линейным (type: single) или ветвящимся (type: branching)
   - Ветвящаяся структура поддерживает рекурсивные подветки (branches)

5. МЕТОД РЕКОМЕНДАЦИИ
   - Используется метод PROMETHEE (многокритериальный анализ)
   - Рекомендации доступны только при полностью заполненном профиле студента
